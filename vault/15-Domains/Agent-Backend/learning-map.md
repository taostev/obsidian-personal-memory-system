# 项目驱动学习路线

## 核心循环

每个阶段遵循同一循环：

1. 从当前业务目标或项目问题出发。
2. 只学习完成当前一步必须理解的概念。
3. 出现设计选择时，比较两到三个业务常用方案及其代价。
4. 用户说明选择理由后再实现。
5. 用测试、运行结果或评测验证。
6. 单独检查是否能解释原理、边界和失败场景。

每次教学只推进一到两个可以执行和验证的步骤。

## 当前阶段

- 阶段：项目选题与 Agent 必要性判断
- 当前重点：选择一个具有真实目标、真实工具、持久状态、权限风险和可评测结果的业务问题
- 暂不决定：最终框架、微服务拆分、多 Agent、RAG、MCP 或具体基础设施

## 渐进式决策点

- 任务路径是否固定：比较普通后端流程、Workflow、Agent 和混合架构。
- 模型、工具、存储是否耦合：比较分层、六边形和插件架构。
- 任务是否长时间运行且需要恢复：学习状态机、任务队列、事件驱动和 Durable Execution。
- 是否存在并发、重试和重复执行：学习异步 Worker、幂等、限流、超时和补偿。
- 单 Agent 是否出现工具过多或上下文污染：再比较 Skills、Router、Subagent、Handoff 和多 Agent。
- 是否需要独立扩缩容或团队自治：再比较模块化单体和微服务。
- 是否需要审计和复杂读写模型：再评估 CQRS 或事件溯源，不默认采用。

## 学习材料原则

- 教程、开源 Harness 和框架只在当前问题需要时作为参考实现。
- 优先理解最小原理和接口边界，再学习框架封装。
- 不为覆盖名词而堆叠架构；每项技术必须对应一个真实问题和验证结果。
